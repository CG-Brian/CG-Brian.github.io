## The challenge

The input was a family of Cause & Effect engineering spreadsheets: documents that describe which equipment signals (causes) trigger which operational actions (effects), with the relationship recorded at the intersection of a row and a column. Different vendors, owners, projects and teams write them differently, even when they describe the same underlying concepts.

That variety shows up as:

- merged cells, hidden rows and columns, and strikethrough formatting;
- multiple header rows, and sparse or fragmented data;
- inconsistent tag naming and differently arranged cause and effect axes;
- voting and logic annotations, legends and notes;
- relationships encoded at matrix intersections;
- conflicts between the primary matrix and a supplementary reference list, such as an IO list.

The objective wasn't converting Excel to JSON. It was a dependable pipeline that extracts spreadsheet structure, interprets heterogeneous industrial semantics, normalizes entities and relationships consistently, and keeps every value connected to its source.

## Parsing structure before semantics

<StoryBrief
  problem="The input wasn't a database table but a human-authored workbook, where header positions, merged regions and formatting carry meaning. A generic reader can return every cell value correctly and still misrepresent the document, and handing the whole workbook to an LLM made the system ambiguous and hard to test."
  contribution="I developed the deterministic parsing and preprocessing layer that turns ExcelJS workbook representations into structured raw engineering records before any semantic normalization."
  decision="Extract by explicitly configured read regions and original spreadsheet coordinates, and resolve merges, hidden and struck content and matrix intersections in code, where the behavior can be tested."
  outcome="A deterministic extraction layer that gives the LLM predictable, structured raw rules with their source coordinates. No accuracy or throughput benchmarks are claimed."
  outcomeLabel="Outcome"
/>

The parser works from the serialized ExcelJS model, with its workbooks, worksheets, rows, cells and merge ranges, and reconstructs the document's structure from it. Configured read regions tell it where the cause columns, effect headers and matrix live; coordinates tell it what belongs to what.

<Figure caption="Synthetic sheet and rule. Real workbooks are larger and messier, but the mechanics are the same.">
  <ParserDiagram />
</Figure>

The details that mattered:

- **Merged cells.** A merged range stores its value only in the anchor cell; every other position reads as empty. The parser distinguishes a cell's raw value from its resolved merged value, because a merge can be a shared header or a grouped engineering relationship, and the two must be handled differently.
- **Hidden and struck-through content.** Hidden rows and columns and strikethrough can mean a record is inactive. These are handled deliberately rather than treating every cell the same.
- **Multi-row and irregular headers.** Fields can span several header rows or sit in different places from one workbook to the next, so configured source regions map onto output fields explicitly.
- **Matrix intersection semantics.** Causes on one axis, effects on the other, relationships in between. Each raw relationship record keeps entity metadata separate from relationship-specific properties.
- **Vertical merge continuation.** A vertically merged span can mean a continuation row within the same cause group, or a new cause or voting group. Telling them apart meant examining identity cells, merge boundaries and grouping behavior together.
- **Original coordinates.** Source row and column identities are preserved, and hidden rows are never renumbered, so downstream consumers can reconnect normalized results to the original sheet.

### The bug that coordinates fixed

One recurring failure came from sequence-based mapping. Filtering out empty cells and then zipping the remainder with the headers shifts every later value into the wrong field as soon as a merge or blank appears. I investigated these mismatches and moved extraction onto original coordinates instead of the order of filtered cells.

## Automatically finding the right data

<StoryBrief
  problem="Even a deterministic parser needs to know where to read, and every team places cause headers, effect headers, tags, descriptions, IO-list fields and matrix boundaries somewhere different. Configuring every workbook by hand made the application slow to use."
  contribution="I developed automatic inference logic that suggests read regions and field mappings from irregular workbook structures."
  decision="Inference proposes where to read; the deterministic parser extracts only from settings a person has confirmed. Heuristics handle the clear cases, and LLM-assisted interpretation is reserved for the ambiguous ones."
  outcome="Less manual setup with human control kept over the configuration. No user-time savings are claimed."
  outcomeLabel="Outcome"
/>

The inference looks at worksheet dimensions and used regions, merged-cell structure, candidate header locations, domain terms such as TAG and DESCRIPTION, distinctive field-name patterns, where the cause and effect axes run, matrix intersection regions, IO-list structure, and how headers sit relative to their data.

<Figure caption="Synthetic suggestions. Ambiguous fields are flagged for confirmation rather than guessed.">
  <ReadSettingsInference />
</Figure>

The separation is the point. Inference is probabilistic and can be wrong; extraction is deterministic and must be right. Keeping a preview and confirmation step between them means a bad suggestion costs a correction, not a corrupted dataset.

On status: earlier snapshots had the inference logic working before its API endpoint was fully connected, and later development records describe the capability as implemented. I describe it as developed automatic read-settings inference rather than claiming a fully deployed autonomous workflow.

Automating configuration is often worth more than replacing a reliable deterministic parser with another probabilistic process.

## Improving normalization reliability

<StoryBrief
  problem="Correct structure doesn't guarantee correct meaning. Owners and vendors express the same equipment concepts with different field names, abbreviations and annotations, so a correctly extracted relationship could still be interpreted wrongly."
  contribution="I ran detailed field-level error analysis on normalization output and improved it through changes to LLM normalization behavior, structured-output constraints and deterministic post-processing."
  decision="Fix recurring failure modes where they come from, by field and by document convention, instead of rewriting prompts until a few examples look right."
  outcome="Improved rule-level normalization accuracy and substantially reduced unsupported relationships. Internal benchmark figures stay private."
  outcomeLabel="Outcome"
/>

The difficult fields were the ones where domain meaning is compressed into a few characters: equipment identifiers, signal types, action semantics, delay times, RESET behavior, MOS flags, voting logic, tag naming, and cause and effect attributes.

<Figure caption="Synthetic failure modes, written to show the categories rather than any real document.">
  <ErrorAnalysis />
</Figure>

The recurring problems:

- **Inconsistent owner conventions.** The same property could appear under different abbreviations or layouts. A prompt that worked for one owner's documents could misread another's, so the pipeline had to absorb variation without inventing fields.
- **Hallucinated relationships.** The model could infer a cause–effect link the matrix didn't contain. In this domain, a false relationship changes the engineering logic itself, so it's among the most serious errors.
- **RESET and MOS semantics.** These could be propagated across several records or treated as generic defaults. Explicit source values had to be distinguished from inferred or unrelated metadata.
- **Duplicate tags and split identifiers.** Tags repeated across rows or written in inconsistent formats needed consistent, domain-aware interpretation.
- **Missing attributes.** An absent value had to stay absent, not be filled with something plausible.

My approach was iterative. I identified recurring error patterns, grouped them by field and document convention, refined the semantic normalization instructions, tightened structured-output constraints, applied deterministic correction where a rule was the right tool, validated corrected results against reference records, re-ran the evaluations, and checked specifically for unsupported relationships. Looking at failures per field (cause identity, effect identity, IO type, action, delay time, voting, relationship presence) showed what an aggregate score hid.

Evaluation snapshots over the internship used different metrics and datasets, so I don't combine them into a headline number. Where an item still couldn't be normalized reliably, the pipeline said so explicitly rather than filling the gap:

## Rethinking the unit of normalization

<StoryBrief
  problem="The original pipeline normalized each relationship record on its own, so a cause that appeared in several relationships was reinterpreted each time, in different context, and could come out with conflicting identities. Effects had the same problem."
  contribution="I worked within the team's transition to entity-level normalization, on its evaluation, post-processing, integration and the consistency requirements it created downstream."
  decision="Normalize each unique cause and effect once, normalize relationship attributes separately, and assemble the rules deterministically."
  outcome="One identity per shared entity, and intersection-specific information kept with the right relationship."
  outcomeLabel="Outcome"
/>

The move to entity-level normalization was a team-level architectural decision. My contribution was helping make the resulting pipeline consistent and reliable across heterogeneous documents.

<Figure caption="Synthetic example. The readings are invented, and no accuracy or token figures are implied.">
  <EntityOnceDiagram />
</Figure>

The revised flow:

1. Extract raw relationships deterministically.
2. Collect the unique causes and the unique effects.
3. Normalize each entity **once**, with stable context: its own source fields, applicable legends and annotations, and relevant reference data.
4. Normalize relationship attributes separately.
5. Assemble the rules deterministically.

Underneath is a data-model distinction that has to hold throughout: entity identity, entity attributes and relationship attributes are different things. An action at a cause–effect intersection isn't a property of either entity on its own.

<Figure caption="Three synthetic sources, two targets, four relationships.">
  <MatrixToGraph />
</Figure>

Two downstream implications came with it:

- **Shared identity.** A common entity must not get a different normalized identity depending on which relationship is being processed.
- **Ordering.** The normalized rule list doesn't necessarily preserve the physical order of the matrix axes, so explicit row and column anchors are needed to rebuild the original document's layout in the UI. That connects directly to the next section.

The unit of model inference doesn't have to be the unit of the final output.
</Pull>

## Making every value traceable

<StoryBrief
  problem="A normalized engineering record isn't useful for review if nobody can see where its values came from. A value might come from the matrix, the IO list, a reconciled reference, an LLM interpretation or a deterministic correction, and the sources can disagree."
  contribution="I designed and implemented a field-level provenance contract, built around TrackedValueDTO, that carries traceability from the normalization pipeline through the backend APIs to the frontend review interface."
  decision="Make provenance part of the data contract for every field (value, source, source cells, conflict), plus explicit row and column anchors on every rule, instead of logging it on the side."
  outcome="Reviewers can see which source supplied a value, the cells behind it, and any competing value, and can jump to the source in the sheet."
  outcomeLabel="Outcome"
/>

Conceptually, every normalized field is wrapped like this. It's an illustrative shape, not the private schema:

```typescript
type TrackedValueDTO<T> = {
  value: T | null;
  source: "CNE" | "IO_LIST" | string | null;
  source_cells: string[];
  conflict: ConflictInformation | null;
};
```

- **value**: the normalized value, or `null` when it's genuinely missing.
- **source**: the document or source category that supplied it.
- **source_cells**: the original A1-style cell addresses behind it.
- **conflict**: competing values and their own provenance, when sources disagree.

<Figure caption="Synthetic Cause & Effect example. One field, its two sources, the conflict, and what the reviewer sees.">
  <TrackedValueTrace />
</Figure>

The contract changed more than single fields. Each rule now carries a single relationship effect instead of an ambiguous repeated effect structure, explicit cause row anchors and effect column anchors, field-level value wrappers, and source alternatives on conflicts. Together these connect normalized data back to the document it came from.

### Across service boundaries

<Figure caption="Conceptual flow. The backend owns state; the processing service owns the transformation and its contract.">
  <TraceFlow />
</Figure>

The backend handled the broader stateful responsibilities, and the frontend owned the review interface. My direct work was on the data contracts and traceability semantics both of them consume.

### Provenance isn't automatically truth

An LLM can return a perfectly plausible source cell that doesn't support the value it's attached to, and evaluation did turn up provenance mismatches and invalid references. So the system distinguishes three levels: a **valid** A1-style address, a cell that **exists**, and a cell that actually **supports** the value. In the UI, record-level navigation relies on the rule's row and column anchors, and field-level highlighting uses source cells only where they're reliable. I don't describe approximate reverse mapping as fully verified.

### Keeping conflicts visible

When the matrix and the IO list disagree, defined reconciliation rules decide which source takes precedence for which kind of information, and the alternative value keeps its own provenance for review. A reviewer sees not only the selected value but why it was chosen.

## Lessons learned

### Parse structure before asking for meaning

Merged cells, coordinates and hidden rows are deterministic problems. Solving them in code made the model's job smaller and the whole pipeline testable.

### Automate configuration, keep extraction deterministic

Inference is most useful when it proposes settings a person can confirm, not when it replaces the parser.

### Study the shape of the errors

Field-level, convention-level error analysis found problems an aggregate score couldn't, and pointed at whether the fix belonged in the instructions, the schema or a deterministic rule.

### The unit of inference is a design choice

Normalizing entities once and relationships separately removed a structural source of inconsistency that no prompt change could.

### Provenance is a contract

Traceability only helps review when it's part of the data model itself, verified against the source, and carried across every service boundary.
